2026-10-10 性能检查

结论：当前实现确实存在高 CPU 和可感知卡顿风险。macOS 的菜单栏循环动画已通过隔离实验复现持续 CPU 开销；跨平台桌面端的服务器列表存在重复渲染和大列表同步重建；两端共用的历史查询、远程同步会随着数据增长变慢。短时间采样未证明存在持续内存泄漏，也不能排除长期泄漏。

本次只检查并新增报告与本地测量文件，没有修改应用代码、用户配置或正在运行的实例。没有连接远程服务器，远程采集脚本通过本地合成文件测试。

测量环境：Intel i7-9700 / 8 个逻辑 CPU / 32 GB 内存，macOS 26.7.1。CPU 百分比以一个逻辑核心为 100%，不是整机百分比。机器存在其他负载，数据用于定位问题，不作为跨机器性能承诺。

同时运行的两份应用均显示版本 0.1.26 (27)，但构建文件和数据目录不同，不能因为版本号相同就认为运行代码等同于当前工作区。连续 top 采样共 16 次，剔除首个无差分样本，后续 15 次统计如下。采样时未主动操作这两份应用，窗口和会话状态保持现场状态，不能称为“无活跃任务的空闲基线”。

| 进程 | 平均 CPU | 观测范围 | 末次 top MEM |
| --- | ---: | ---: | ---: |
| 安装版 macOS 界面，PID 89012 | 56.2% | 17.5–83.8% | 272 MB |
| 安装版主查询核心，PID 89015 | 16.0% | 0–70.4% | 83 MB |
| dist 开发版 macOS 界面，PID 91585 | 40.9% | 7.4–57.7% | 82 MB |

MEM 是 top 的进程内存口径，不是安装包大小，也不是整个进程树总内存。表中没有把其他配置、采样、网络子进程和系统 WindowServer 内存加进去。两个应用同时运行会叠加开销。sample 记录的主核心历史 physical-footprint 峰值约 336 MB / 316 MB，说明存在阶段性内存峰值；峰值本身不等于泄漏。

1. **高优先级：macOS 菜单栏的持续动画。**

   `apps/macos/Sources/Aieyes/SessionActivity.swift:100` 对活跃会话应用 `.symbolEffect(.pulse, options: .repeating)`；菜单栏在第 112 行直接使用它，`surfaceActive` 默认值为 true（第 140 行）。详情窗口隐藏会关闭自己的动画，但菜单栏会继续动画。

   复用当前 SwiftPM debug 构建中的生产 `MenuActivityLabel`，关闭 AppModel 自动启动和全部后台工作，只创建一个菜单栏状态项。每个状态预热 1 秒、测量 7 秒，用进程 getrusage 的 CPU 时间差除以实际墙钟时间；对相同图标只改变 `surfaceActive`：

   | 状态 | 循环动画 CPU | 关闭动画 CPU |
   | --- | ---: | ---: |
   | 思考中 | 25.77% | 0.020% |
   | 进行中 | 22.75% | 0.028% |
   | 执行工具 | 3.94% | 0.006% |
   | 空闲，前后基线 | 0.019% / 0.021% | — |

   已运行进程的 sample 也集中出现 `CA::Transaction::commit`、`RBLayer display`、SwiftUI 布局与绘制，开发版核心在同期主要阻塞等待 stdin，支持优先调查界面绘制。隔离实验确认动画自身的成本，但不能把现场界面的全部 40–56% 都归因于这一个组件。

   建议先把常驻菜单栏改成静态状态，或只在状态切换时做有限次数动画。把菜单栏所观察的状态收窄到会话阶段、数量和所选统计值，避免 AppModel 任意属性改变都触发布局。

2. **高优先级：桌面端服务器页一次采样两次渲染，且折叠内容仍完整生成。**

   `apps/desktop/src-tauri/src/main.rs:94` 为 `hosts.sample` 生成 `desktop:hosts` 广播，第 324 行发送事件。前端 `apps/desktop/web/app.js:1028` 接收广播后执行 `applyHostSamples`；发起采样的同一窗口又在第 265 行收到 RPC 返回后执行一次。`applyHostSamples` 在第 252 行直接触发服务器页 `render()`。

   复用实际前端、事件处理和 sample 函数，模拟原生 RPC 先广播再返回，记录到一次采样触发 **2 次 render**。实际执行顺序可能受事件调度影响，但两个更新入口都存在。

   `apps/desktop/web/app.js:591` 的 `renderServers` 每次用 `innerHTML` 重建整个服务器页，包括折叠 details 内的 CPU、磁盘等节点。Chromium 151 + Playwright、1120×800、合成 IPC、关闭周期轮询、每场景测量 6 次 renderServers 加强制布局：

   | 主机数 × 每台 CPU 设备数 | 主机卡片状态 | DOM 节点总数 | 单次中位耗时 | 最大耗时 |
   | --- | --- | ---: | ---: | ---: |
   | 3 × 16 | 折叠 | 1,004 | 14.3 ms | 27.3 ms |
   | 10 × 64 | 折叠 | 5,364 | 47.4 ms | 69.9 ms |
   | 30 × 256 | 折叠 | 44,564 | 205.4 ms | 294.6 ms |
   | 10 × 64 | 展开主机卡片 | 5,364 | 40.2 ms | 62.7 ms |

   这些是前端主线程的同步工作，可直接推迟输入与绘制；前台默认约 2 秒采样一次，会反复发生。高规模场景是压力测试，不表示当前用户配置了 30 台主机。测试未测 Windows WebView2、Linux 原生 WebView、GPU 合成或整个 Tauri 进程树，不能把该值当成 Windows 实机基准。

   建议采样结果只由一个入口更新，按主机 ID 更新数值，展开明细时才创建对应 DOM，并对大量设备使用分页或虚拟列表。

3. **高优先级：两端的“今日”概览仍遍历近一年事件。**

   `crates/core/src/store.rs:717` 为热力图把最早查询时间至少推至 364 天前；第 732 行读取事件 payload，第 785 行起逐条反序列化并重新聚合。选择今日不会绕过这部分历史工作。

   新编译的当前工作区 release 核心，使用真实 events、event_sources、price_history 统计表的独立副本；未复制账户、凭据、代理配置。每个范围串行测量 4 次完整 JSON-RPC 请求，表中为中位值：

   | 统计记录数 | 今日 | 最近 30 天 | 最近 365 天 |
   | ---: | ---: | ---: | ---: |
   | 50,304 | 267.3 ms | 298.4 ms | 382.3 ms |
   | 105,465 | 464.1 ms | 504.8 ms | 772.6 ms |

   这不是对已安装旧构建的 RPC 测试，也不是完整私人配置的重放。数据来自不同数据库，分布不同，不能仅凭两行推断严格的线性斜率。

   macOS 的 `EngineClient.swift:304` 的 reload 在非“今日无筛选”场景还会额外查询无筛选今日数据，用于菜单栏。两端都有请求序号来防止旧结果覆盖新结果，但不会取消已经排队的查询：macOS `EngineClient.swift:4,43` 使用串行队列，Tauri `main.rs:287` 在后台线程持有同一路 Engine 的互斥锁。历史同步、限额查询和 dashboard 共用主要工作队列，慢 SSH 或快速连续切换筛选会延长数据等待；这与直接阻塞界面线程的卡顿是两类问题。

   建议把每日/模型聚合与热力图增量维护或缓存，菜单栏读取轻量摘要；为 dashboard 采用独立只读通道，并在执行之前合并已经过期的筛选请求。

4. **高优先级（使用 SSH 历史来源时）：远程历史同步每次全量读、全量传。**

   本地 JSONL 导入在 `crates/core/src/import.rs:91` 之后已有文件游标，可以只读新增部分；远程 `scripts/remote_history.py:152` 遍历目录，第 165 行起从头读取所有日志，积累完整统计事件后一次输出。`crates/core/src/lib.rs:309` 调用时只传目录和 provider，没有上次游标；第 351 行起再次处理全部返回事件并执行入库/去重。没有新记录时仍会承担读取、JSON 解析、传输、去重的成本。

   用一个 43,537,906 字节的合成 JSONL 文件，在本机直接运行同一远程脚本两次（未建立 SSH）：第二次文件完全未变，仍花费 **813 ms 墙钟 / 0.703 秒 CPU**，返回 **1,798,044 字节、10,002 条统计事件**。这是采集脚本本身的成本，未计网络和接收端解析入库。实际远程机器性能可能不同。

   代码有统计结果约 48 MiB 和子进程输出 64 MiB 上限，但上限不限制需要扫描的原始日志总量，JSON 对象和原始缓冲也会同时占用内存。远程来源每批最多 3 个并行，所有批次结果暂存在 fetched 中，因此不能把单条输出上限理解成整个应用的峰值内存上限。

   建议增加每文件 offset、签名和截断检测，让远程端输出增量；按批次消费结果并释放内存。错误时保留已有统计并延后重试。

5. **中优先级：刷新配置、常驻调度和批量主机采样。**

   安装版数据库当前保存 `refreshSeconds=10`，没有独立 historyRefreshSeconds；旧配置迁移规则在 `crates/core/src/models.rs:465` 继承原刷新间隔。开发版保存 historyRefreshSeconds=300、refreshSeconds=300、后台主机 10 秒、前台主机 2 秒。这会让两份应用的工作频率明显不同。前述安装版核心较高占用与更频繁工作相符，但缺少完整符号和逐 RPC 追踪，不能精确分摊到某个请求。

   macOS `EngineClient.swift:289,610` 与桌面端 `app.js:1057` 都每 0.5 秒检查任务；会话读取每 5 秒一次，目录发现每 30 秒一次。它们有忙碌保护，不能直接把 0.5 秒定时器说成“每半秒全量采集”。原生视图也已经依据窗口可见性停用部分 Timeline 和动画。

   `crates/core/src/lib.rs:476` 的主机采样为每个启用的主机创建线程，没有统一并发上限，且等待整个批次结束后才统一返回。SSH 子进程还创建输入/输出/错误读取线程；单次远程调用最长等待 45 秒。多主机、大量失败连接或慢主机会增加线程、进程、缓冲区占用，并推迟健康主机读数显示。少量主机不等于必然高占用。

   当前 release 核心的本机采样单独测量 6 次，首次 310 ms（含 CPU 初始预热），之后约 20–25 ms，未显示本机指标采集是这次持续高 CPU 的主因。

   建议给历史、限额和主机采样保留独立频率；按下一次到期时间唤醒，失败使用退避；主机采样限制并发并允许逐台返回。用户主动选择的高频采样设置应予保留。

建议处理顺序：菜单栏无限动画 → 服务器页重复渲染与折叠明细 → dashboard 聚合缓存和查询队列 → 远程历史增量 → 调度与并发优化。现有后台执行、忙碌保护、网络缓存、本地文件游标和子进程超时机制是有效基础，不需要把整个架构推倒重写。

- `top-30s.txt`、`top-summary.json`：现场连续采样。
