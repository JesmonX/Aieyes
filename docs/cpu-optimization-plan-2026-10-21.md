# CPU 与界面响应优化计划

依据：[交互性能排查报告](cpu-interaction-audit-2026-10-21.md)。P0、P1 已实施，实施和验收情况见[优化结果](cpu-optimization-results-2026-10-21.md)。CPU、内存卡片等高已单独完成并验证。

按用户补充要求，复测缩减为 6 个关键场景、每项 5 次，并加一组状态与 IPC 回归；下文原定性能门槛保持不变。排查阶段的 20 次数据仍作为原始依据，不再运行安装版与工作区版本差距测试。

范围以当前工作区的 macOS 主窗口、浮动面板和菜单栏为主，覆盖滚动、滚动中刷新、点击、筛选、切页和操作后回落。后续只验证当前实现的修改前后，不继续比较安装版与工作区版本。

## 依据与优先级

同一 Release 配置与实际规模数据、每组 20 次测量：

| 场景 | 当前每轮 CPU 中位数 | 暂停滚动位置写入的配对控制 | 当前 / 控制的滚动步进 P95 中位数 |
| --- | ---: | ---: | ---: |
| 分析页滚动 | 11,027 ms | 273 ms | 391 / 18.5 ms |
| 面板滚动 | 9,096 ms | 150 ms | 293 / 18.7 ms |
| 面板滚动中刷新 | 10,499 ms | 1,196 ms | 317 / 140 ms |

滚动位置写入引发的通知链具有直接对照证据，优先处理。停止该写入后，刷新期间仍有明显停顿，因此刷新发布需要单独优化。只保留活动页使切页 CPU 从约 2.41 秒降至 2.05 秒，收益不足以支持先做大规模页面生命周期重构。

以上是原生驱动指标，包含显式布局、5 ms 心跳和模拟滚动回退；不是硬件输入延迟或屏幕帧率。控制组只说明优化方向和可达到的参考水平，不能视为产品修复已经实现的收益。

## 第一阶段：滚动写入与偏好通知（P0）

涉及 `MainWindowView.swift` 的 `ScrollMemory`、`PetWindow.swift`、`SessionActivity.swift` 与 `AieyesApp.swift`。

1. 将滚动位置的实时状态保存在内存，按原有页面 key 隔离；连续滚动期间不逐步写入 `UserDefaults`。初始采用最后一次变化后约 250 ms 合并保存，同值不写。
2. 切页或滚动容器拆卸时保存该 key 的最终位置；正常窗口关闭与应用退出时同步收尾。重新挂载优先恢复内存中的最新位置，持久化仍兼容原有 `view.scroll.v2.*` 数据。
3. 区分位置恢复、内容尺寸变化和用户滚动，避免恢复中的临时零坐标、隐藏页尺寸或旧协调器的延迟任务覆盖新位置。保留现有“数据就绪后恢复、位置按内容边界夹取”的行为。
4. 桌宠订阅偏好通知时先比较它实际使用的 enabled/scale 等配置快照；配置未变就不调用窗口同步。仅在可见性发生转换时 orderFront/orderOut，写入 `live.petVisible` 前比较新旧值，遮挡回调也使用相同门控。
5. 复用现有 `MenuStatusStore` 的去重投影，让菜单标签内容或相关显示偏好改变时才重新测量尺寸。编辑未保存标记、tooltip、屏幕缩放和无障碍变化保留独立更新路径，不能因减少标题更新而失效。

验收先确认机制：纯滚动不再引起无关的 `petVisible` 发布或菜单尺寸测量，连续一轮滚动只在静默或生命周期边界合并保存最终位置。再检查分析页和面板滚动各 5 次，CPU 中位数较当前基线至少下降 80%，步进 P95 中位数目标不超过 33 ms。

必须覆盖“滚动未满 250 ms 就切页/关闭”“关闭重开”“内容缩短”“刷新不重置位置”和两个窗口使用不同 key。正常退出应保存最终位置；强制杀进程可能丢失尚未落盘的一小段位置，需明确这是延迟保存的边界。

## 第二阶段：刷新与可见区域状态发布（P1）

涉及 `EngineClient.swift` 的 `reloadOnce`、状态应用及 RootView/SessionStrip 的观察范围。

1. 利用现有 revision、scope cache 和请求编号，在 revision、筛选及有效数据均未改变时不重新赋值 dashboard、估值数组、scope 文本和模型选项。时间戳若需要显示，单独更新对应的小区域。
2. 将同一次刷新得到的数据整理完成后统一应用，减少多次嵌套字段赋值引起的中间渲染。保留加载、成功、错误和部分失败反馈；已经为空的错误、未变化的状态不重复发布。
3. 优先在现有实现上做同值与批次门控，再给总览、分析、面板和会话条建立各自所需的稳定投影。会话条只因会话、来源健康等可见内容变化而更新，不跟随桌宠可见性和动画状态重算。
4. 保留 `dashboardRequest` 的旧响应丢弃、现有刷新合并及 busy 门控。分析、总览和面板的不同筛选不能共享错误结果；核心重启、来源变更和重扫必须使相关缓存失效。
5. 避免用每次整份 dashboard 的 JSON 编码或深度序列化代替变化判断，防止把布局开销转移成主线程比较开销。

机制验收：无变化重载对未变化的数据投影发布为 0；全模型发布次数只作为诊断，不要求加载/错误反馈也为 0。无变化重载的 CPU 中位数目标下降至少 50%；面板滚动中刷新的步进 P95 中位数先降到 100 ms 以内，继续以 33 ms 为目标。操作反馈 P95 目标不超过 100 ms，实际网络完成时间单独统计。

回归覆盖：四类刷新、筛选快速切换、刷新期间切页、连续点击刷新、错误后重试，以及估值窗口与面板同时打开。必须证明旧响应不覆盖新筛选，真实数据和额度变化能及时显示，焦点和未保存输入保留。

## 第三阶段：残余布局与格式化（P2，按复测决定范围）

第一、二阶段达标后重新采样。只有剩余栈仍显示明显的重复测量或隐藏页布局，才扩大到这些改动：

- `BalancedGridLayout`、`FlowLayout` 使用 SwiftUI Layout cache，复用一次布局中的尺寸与排列计算；宽度、内容、字体、列数或间距变化时失效，实际放置宽度不同则重新计算。验收窄宽切换、长文本、动态内容和深浅/高对比外观的几何正确性。
- `Format.date` 复用配置后的格式器，保持现有输出，处理时区变化与并发访问；其他格式器按采样结果再处理。用真实时间戳验证逐项输出一致，不能以微基准倍率声称整应用收益。
- 若隐藏页成本仍显著，再评估每页独立保留的 hosting 容器，让活动页参与主布局；切页前保存必要的页面状态。不能直接把当前 ZStack 改成条件创建并接受编辑草稿、展开项或滚动位置丢失。

这里不预设整体收益。每项单独复测；没有稳定收益或出现状态回归的改动不进入最终实现。

## 首次历史扫描的处理

当前热扫描中位数约 50 ms。首次约 8.85 秒主要来自解析版本升级后的 Codex 历史重读，属于独立的后台工作，不作为上述滚动修复的验收门槛。

保留解析版本失效、历史备份、事务和游标正确性。首次重读更细的来源/阶段进度与取消作为独立后续工作，本轮不改扫描协议；后续实施应保证界面仍可滚动和切页。若真实验收仍受影响，再检查批次与进度节流；不能通过跳过必要重解析、降低统计正确性或缩小数据量来“优化”数字。

## 实施拆分与验证

建议按以下顺序形成可独立审查、回退的提交：

1. 滚动位置合并保存及生命周期回归。
2. 桌宠偏好门控、同值发布保护及菜单测量门控；与第 1 项合并验收 P0。
3. 刷新应用去重和稳定投影；验收 P1。
4. 按残余栈选择布局/格式化改动；页面容器重构单独决策。

沿用排查时的私有快照、固定回放、实际窗口尺寸和主题，不改账户数、价格数或数据量来降低负载。精简复测覆盖分析页滚动、面板滚动、面板滚动中刷新、无变化刷新、进入分析页和刷新切页连点，每项 5 次；状态回归覆盖持久化、卡片操作、旧响应、错误恢复、焦点及未保存编辑。无需重跑 37 类操作矩阵或安装版版本差距矩阵。

验收驱动需同时记录滚动手势阶段和停止后的保存阶段，等待延迟写入完成后再结束一轮，防止把 CPU 开销推到样本之外。记录实际持久化次数、相关状态发布、菜单测量次数，以及手势 CPU、收尾 CPU、超过 33 ms 的步骤和刷新反馈。性能比较使用同一个更新后的驱动与相同输入，只比较该改动前后。

自动化通过后，使用优化构建进行真实触控板/鼠标操作，确认面板滚动、悬停/按钮反馈、刷新到达时的位置和焦点、文字可读性、背景合成及桌宠行为。5 秒观察窗口只作回落检查，持续托盘负担另观察至少 60 秒。Windows/Linux 没有本轮原生验收证据，跨平台共用 UI 或契约如有变更，需要对应回归。

本轮实测达到 P0 的 CPU/步进目标，以及 P1 的无变化刷新 CPU 降幅和滚动中刷新 100 ms 步进目标；更进一步的 33 ms 目标、广义操作反馈 100 ms 目标尚未全部达到。详见优化结果，门槛未降低。按用户精简复测要求，本轮保留已验证的主要收益，不扩大到页面容器和布局缓存重构；既有未提交工作保持原样。
